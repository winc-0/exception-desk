# 异常件协同台

面向第三方仓配公司的异常件协同平台，用来跟进破损、丢件、超时和改址。目前完成了账号、多租户隔离、角色权限、工单主流程、证据管理、承运商索赔跟踪、AI 客户回复草稿和理赔条款 RAG，还没有公网部署。

技术栈：Vue 3 + TypeScript、FastAPI、SQLAlchemy（异步）、PostgreSQL 16、Alembic、LangGraph。

## 本地运行

需要 Python 3.12、[uv](https://docs.astral.sh/uv/)、Node.js 24。不需要 Docker，开发数据库由 Python 依赖内置。

在 `backend` 目录启动数据库、执行迁移：

```bash
uv sync
```

```bash
uv run python -m scripts.dev_db
```

```bash
uv run alembic upgrade head
```

创建公司和第一位管理员。先在 `backend/.env` 里加一行 `DESK_BOOTSTRAP_PASSWORD=至少10位的密码`，再运行：

```bash
uv run python -m scripts.create_tenant --slug demo-north --name 华北演示物流 --email admin@north.example.com --admin-name 演示管理员
```

启动后端：

```bash
uv run uvicorn app.asgi:app --port 8000
```

在 `frontend` 目录启动前端，然后打开 http://localhost:5173：

```bash
npm install
```

```bash
npm run dev
```

如果 `uv` 访问 PyPI 镜像时报 403，说明全局配置的镜像不可用。本项目的依赖锁定在官方 PyPI，可以临时取消 `UV_DEFAULT_INDEX` 环境变量后重试。

## 多租户隔离的设计

隔离不只靠应用代码里的 `WHERE tenant_id = ...`，而是由数据库兜底：

- **行级安全：** `memberships` 和 `tickets` 开启 `ENABLE` + `FORCE ROW LEVEL SECURITY`，表 owner 也受约束。
- **默认拒绝：** 没有设置当前租户时查询返回 0 行，所以代码漏设置的后果是查不到数据，而不是看到全部数据。
- **事务级设置：** 用 `set_config('app.tenant_id', ..., true)`，只在当前事务生效，连接归还连接池后不会串到下一个请求。
- **复合外键：** 工单的创建人和处理人通过 `(tenant_id, user_id)` 引用成员表，数据库层面就不能把工单指派给其他公司的人。
- **最小权限：** 运行时使用 `desk_app`，没有 `SUPERUSER` 和 `BYPASSRLS`，不能修改租户表，也没有 `DELETE` 权限；迁移用单独的 owner 账号。

`tenants` 和 `users` 是全局表，没有 RLS：登录时需要先按公司代码和邮箱查询，而且同一个人可以属于多家公司。接口只能通过成员关系读取用户信息。

## 登录会话的设计

- 令牌放在 `HttpOnly`、`SameSite=Lax` 的 Cookie 里，前端脚本读不到；生产环境默认带 `Secure`。写请求还会校验 `Origin`。
- 每个请求都查库确认账号、成员状态和角色，所以停用账号、调整角色立即生效，不用等令牌过期。
- 退出和改密时会让 `session_version` 自增，已经复制走的旧令牌也会失效。退出是全设备生效。
- 连续失败 5 次锁定 15 分钟。所有失败返回同样的提示，账号不存在时也会计算一次哈希，避免探测邮箱是否存在。

## 工单流程的设计

```text
待处理 → 处理中 ⇄ 等待外部
           ↓
         已解决 → 已关闭
           ↓
        重新打开（回到处理中）

待处理、处理中、等待外部都可以由主管取消
```

| 角色 | 能做的事 |
| --- | --- |
| 仓管 | 上报、评论，处理指派给自己的工单 |
| 客服 | 仓管的全部权限，加上领取无人处理的工单、CSV 导入 |
| 主管、管理员 | 指派任何人、处理任何工单、关闭、取消、重新打开 |

处理人不能关闭或取消自己的工单，关闭需要主管确认。

- **状态机集中管理：** 所有规则都在 `app/ticket_flow.py` 的一张表里。详情接口直接返回当前用户能做的操作，前端不用重复写一遍规则。
- **乐观锁防覆盖：** 每次修改都要带版本号，版本号写进 `UPDATE` 的 `WHERE` 条件。两个人同时操作时只有一个成功，另一个收到 409 并看到最新内容。
- **数据库防重复：** 部分唯一索引保证同一运单的同类异常只有一张未关闭的工单，并发创建和重复导入都绕不过去。
- **审计记录只能追加：** 应用角色对 `ticket_events` 只有 `SELECT` 和 `INSERT` 权限，代码有 bug 也改不了历史记录。
- **工单号：** 每家公司独立编号，由计数器行上的锁保证不重复。按工单号做游标分页，翻页时不会因为新工单而重复或漏掉数据。

CSV 导入支持 UTF-8 和 GBK（Excel 中文版默认另存的编码）。有任何一行不合法就整批不导入，并返回每行的错误；已有同类未关闭工单的行会跳过。第一行是列名，类型和标题必填：

```text
类型,标题,运单号,描述
破损,外箱压损,SF1234567890,客户拒收
```

## 证据和索赔的设计

异常件难的往往不是流程，而是向承运商举证。工单现在可以收集证据，并跟踪索赔到到账。

- **证据清单：** 每种异常有自己的必备和建议证据，规则集中在 `app/evidence.py`。必备证据不齐时不能提交索赔。清单是根据公开资料整理的初版，还没有经过真实用户确认。
- **文件类型看内容：** 按文件头判断类型，不相信扩展名和客户端声明，改名成 `.png` 的 HTML 传不上来。下载时带 `nosniff` 和 `CSP: sandbox`。
- **路径和文件名无关：** 文件路径只由租户和附件 ID 决定，文件名只用于展示。
- **证据不可篡改：** 记录 SHA-256。应用角色没有 `DELETE` 权限，`UPDATE` 只开放作废相关的三列。传错了可以作废，原文件和作废原因都保留。索赔提交后不能再作废。
- **不占数据库连接：** 上传前结束事务，收完文件再重新开始。否则几个人同时用手机传视频就能占满连接池。
- **文件和数据库一致：** 先放文件再提交事务，提交失败就删文件。进程中途崩溃最多留下无人引用的文件，不会出现有记录没文件。
- **索赔状态机：** 准备中 → 已提交 → 已核定 → 已到账；已提交可以被拒赔，被拒后可以补材料再次提交。到账由主管确认。规则集中在 `app/claim_flow.py`。
- **和工单联动：** 索赔进行中不能关闭或取消工单。两边都先锁工单行，并发时不会出现已关闭工单上还有进行中的索赔。
- **金额：** 数据库和接口都用整数分，前端按字符串转换，不经过浮点数。仓管看不到金额。
- **到账比例：** 到账金额 ÷ 已有结果（到账或被拒）的索赔金额。进行中的索赔不计入，否则比例会被压低。

## AI 回复草稿的设计

一次访谈里，对方说最费时间的不是流程，而是和客户对接。所以 AI 先做这件事：根据工单和证据情况，起草一条发给客户的回复，由客服确认后自己发出。

```text
agent ⇄ tools（只读工具：工单、证据、索赔）
  ↓
check（代码校验）→ 不合格，带着原因重写一次
  ↓
通过则结束；仍不合格或模型出错，用模板兜底
```

- **事实由代码给：** 缺哪些材料、有什么风险都是规则算出来的，模型只负责组织语言。没有配置模型时功能照常可用，只是回复来自模板。
- **工具没有参数：** 工单在构建图时就绑定了，模型读不到别的工单。工具全部只读，也没有发送动作，所以被提示词注入骗了也做不了什么。
- **校验写在代码里：** 不能承诺赔付，金额和单号必须来自工单事实，不能出现手机号和卡号，缺的必备材料要写全。模型第二次仍不合格就退回模板。
- **尽量少外发：** 发给模型的只有工单类型、标题、描述和证据类别，不含评论、文件名和员工姓名，描述里的手机号、证件号和卡号会先隐藏。
- **不占数据库连接：** 先取好事实并提交事务，再调用模型。模型跑几十秒也不影响连接池。
- **可以统计效果：** 每次记录来源、重写次数、token、耗时，以及客服是直接用、改后用还是没用。

## 理赔条款 RAG 的设计

客服向承运商索赔时，常常说不清对方会用什么理由拒赔、还缺什么证据、能怎么反驳。工单详情页的“索赔依据”根据工单情况查找法规、承运商条款和判例，列出这三项，每项都带可点击的来源。结果只给内部参考，不发给客户，也不构成法律意见。

```text
工单事实（隐藏手机号等）→ 混合检索 → 带上对应承运商的条款
  ↓
generate → check（代码校验）→ 不合格，带着原因重写一次
  ↓
通过则结束；仍不合格、超时或模型出错，用规则版兜底
```

- **语料：** `backend/kb` 里有 61 份公开资料，包括法规、承运商条款、判例和分析文章，每份都标了来源和可信度。其中 10 个判例留作考题，不进检索库，所以可检索的是 51 份。来源和使用须知见 [`backend/kb/README.md`](backend/kb/README.md)。
- **不用向量数据库：** 语料只有 51 份，部署目标是 2 核 4G。向量提前算好放进仓库，启动时加载到内存，少运维一个服务。
- **混合检索：** BM25 用中文单字和双字切词，再和向量余弦的排名做 RRF 融合。向量服务不可用时只走关键词，功能不受影响。
- **条款不靠碰运气：** 别家承运商的条款直接过滤，对应承运商的条款一定带上，因为它决定限额和时效。限额和时效由代码从结构化字段取出来展示，不经过模型。来源较弱的条款会提示核对。
- **只能从分类里选：** 拒赔理由、证据和反驳都从 `taxonomy.json` 的代码里选，并且必须引用这次检索到的资料。
- **校验写在代码里：** 引用的资料必须存在，拒赔理由和反驳至少要引用一份标注了这一项的资料，数字必须来自工单或所引用的资料，不能写“一律”这类绝对结论，已保价不能选未保价相关的理由，未保价不能主张“保价已付对价”，已有的证据不能列为缺失。
- **引用校验的边界：** 只核对资料的标签，不判断这句话是否真被原文支持，所以还是可能有“标签对得上、句子说过头”的情况。证据项没有按资料标注，暂时不核对。这次检索没有资料涉及的理由和反驳，不会提供给模型选。
- **规则版兜底：** 不调用模型，只按检索结果上的标签统计。不配模型也能用，模型 60 秒没有结果也会退回。
- **不占数据库连接：** 和回复草稿一样，先提交事务再调用向量和模型，并且共用每人每小时的次数限制。

v4 的退回有两个原因：工单自己写的金额被当成编造，页面上本来就显示的资料编号也被拒绝。修正后 v5 剩下的退回基本是该拦的，比如引用了别处的金额、把“工单描述”写成资料编号。

v6 的代价是召回率。K05、K06、R14 只出现在留出的判例里，没有可检索的资料，现在选不了，所以 7 项反驳答案最多只能答对 5 项（71%）。这是有意的取舍：没有资料依据的结论不展示。三轮的退回，最后一次的原因都不是新校验：留出组 2 次是金额或倍数不在所引资料里；回放组 8 次里 7 次也是这个问题，1 次是模型连接失败，当时六组评测在同时运行。

这 10 个案例调提示词时反复看过，所以又回放了 19 个没用过的案例：语料里的判例和媒体报道，回放时把案例自己排除在检索之外。语料里还有 7 个案例没有用：5 个原文没有披露具体事实，2 个没有拒赔理由标签。

```bash
uv run python -m evals.run_brief --set replay --mode model --show
```

为了判断分数高低，还加了一个一行规则当基线：未保价就猜“未保价限额”，已保价就猜“保价不足额或按比例”。下面只比较拒赔理由，brief-v5 的两组各跑三轮：

| 方法 | 留出 10 例（21 项答案） | 回放 19 例（28 项答案） |
| --- | --- | --- |
| 一行规则 | 100% / 38% | 94% / 57% |
| 规则版（检索标签统计） | 38% / 52% | 37% / 71% |
| brief-v5（模型） | 44-50% / 52-57% | 50-62% / 82-86% |
| brief-v6（模型） | 65-79% / 52% | 57-68% / 75-82% |

回放时 19 例退回规则版 1-3 次，退回的原因大多是校验拦下了别处的金额（比如 280 元、4.98 万元），或者模型把“工单描述”当成资料引用。没有因为这组结果修改提示词，否则它也不再是没用过的数据。

能得出的结论有限：

- **模型的价值是列得全，不是猜得准：** 一行规则的精确率远高于模型，因为大多数案例的主要理由就是未保价限额，29 例里有 17 例。模型多找到了一些理由，代价是误报明显增多。索赔前做检查时漏掉一个理由的代价通常更高，所以这个取舍可以接受，但这是我的判断，没有测量过。
- **模型比规则版好一些：** brief-v5 拒赔理由的精确率和召回率都更高。在留出组上，缺失证据只比规则版略高，反驳的召回率更高。brief-v6 的精确率更高，但留出组的拒赔理由召回率和规则版持平，都是 52%。
- **缺失证据和反驳分数只看留出组：** 回放组大多是媒体报道，没有标注这两项（19 例里只有 8 例有），只有 8 项和 4 项答案，这两项的分数没有意义。模型还爱重复列价值证明和签收验视记录，回放第一轮 19 例里分别出现 15 次和 11 次。
- **向量没有测出优势：** 判决或报道里的拒赔理由有多少出现在取回文档的标签上（k=8）：29 例合计关键词 38/49，向量和混合都是 37/49，只差 1 项。这个指标比较粗，回放组三种方法都是 25/28，可能已经到顶，分不出差别。目前保留混合检索，是因为成本很低，而且案情和资料措辞不同时可能有帮助，但这一点还没有证据。
- **分数不能当准确率：** 样本很少；案情是看过原文后手写的，虽然回放组写的时候没看答案标签，但原文里有裁判结果；回放用的案例也可能被别的文档提到；同一版本多跑几次也会波动几个百分点；判决没提到的证据不算标准答案，所以缺失证据的精确率偏低。

## 部署

```bash
cp .env.example .env
```

填好 `.env` 后启动。附件保存在 `attachments` 命名卷里，备份时要和数据库一起备份。

```bash
docker compose up -d --build
```

CI 会用生产镜像跑 `scripts/smoke.sh`，检查建公司、登录、建工单、上传 6 MB 文件、下载比对，以及重建 API 容器后文件还在。

### 服务器连不上 Docker Hub 时

先在 GitHub 上手动运行 `Publish images` 工作流，它会构建镜像并推到镜像仓库。工作流需要这些设置：

- 变量：`ACR_REGISTRY`（仓库地址）、`ACR_NAMESPACE`（命名空间）
- 密钥：`ACR_USERNAME`、`ACR_PASSWORD`

然后在服务器的 `.env` 里把 `DESK_IMAGE_PREFIX` 设为 `仓库地址/命名空间`，登录仓库后拉取并启动：

```bash
docker login 仓库地址
docker compose -f docker-compose.yml -f docker-compose.registry.yml pull
docker compose -f docker-compose.yml -f docker-compose.registry.yml up -d
```

## 已知限制

- 失败锁定按账号计算，别人可以故意输错让某个账号暂时无法登录。上线前还要在反向代理层按 IP 限流。
- 成员的初始密码由管理员设置和告知，还没有邮件邀请和首次登录强制改密。
- 列表搜索是简单的模糊匹配，没有全文索引，数据量很大时会变慢。
- 导入有重复行时，被跳过的行也占用工单号，所以工单号可能不连续。
- 前端测试是组件级的，工单列表、证据上传和成员管理页面还没有覆盖，也没有端到端的浏览器测试，这些仍靠手动验证。
- 校验只能拦规则能表达的错误，语气是否合适、理解是否准确还要靠人确认。
- 流式显示的文字在校验前就出现了，校验不通过会被清掉。界面会提示校验前不要使用，并且在校验完成前不能复制。
- 起草次数按人限制每小时 30 次，并发请求可能略微超出；还没有按公司限制成本。
- 索赔依据的校验管不了推理是否站得住。试用时见过模型依据不足就主张“可能构成重大过失”，需要客服自己判断。
- 部分承运商条款不是官网直取：顺丰来自媒体转述，中通来自搜索摘要，EMS 来自第三方转载，京东是上门取件协议。页面会提示核对，详见 `backend/kb/README.md`。
- 语料是一次性整理的静态文件，条款更新要手动替换并重新计算向量，还没有定期更新机制。
- 索赔依据还没有在真实工单上验证过，也没有请理赔或法律从业者审核过。
- 附件只存本地磁盘，单机部署可用；多实例要换成对象存储。
- 每张工单最多 50 份证据、单个 50 MB，但没有按公司限制总量，也没有病毒扫描。
- 进程崩溃可能留下无人引用的文件，目前没有定期清理。
- 证据清单对所有承运商和货主都一样，还没有按承运商或货主配置。
- 容器只提供 HTTP，公网部署时要在前面加 HTTPS 反向代理；否则默认带 `Secure` 的 Cookie 发不出去，无法保持登录。
